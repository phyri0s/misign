# 0008 — Packaging and releases

- **Status**: accepted
- **Date**: 2026-09-25

## Context

ADR 0004 sets the release pipelines: every merge into `dev` publishes a pre-release, every merge into `main` a stable release, with SemVer versions and a changelog generated by release-please from Conventional Commits. This ADR records how the application is packaged on each OS and how those pipelines work in practice.

Constraints: no code signing certificate for now, GitHub Releases as the only distribution channel, no Docker in CI or in the application.

## Options considered

- **Windows**
  - MSI (CPack + WiX): standard for managed deployments (GPO, Intune), but more tooling, and less familiar to individual users.
  - MSIX: modern, clean updates, but an MSIX not signed by a trusted certificate does not install normally.
  - NSIS installer (CPack NSIS): a classic `setup.exe`, familiar to individual users, NSIS is preinstalled on GitHub's Windows runners, and it works unsigned (with a SmartScreen warning).
- **Linux**
  - AppImage (linuxdeploy and its Qt plugin): a single executable file, no installation and no runtime to install, simple to build in CI and to publish on GitHub Releases.
  - Flatpak: sandboxed (network access could be denied), updates through Flathub, but needs a manifest, a KDE/Qt runtime and a Flathub submission to be useful.
- **Dev pre-releases**
  - Published automatically on every merge into `dev`.
  - Through a release-please pull request on `dev` too: one more manual step for every pre-release.
- **Merge method on `dev`**: merge commits make release-please count both the pull request title and each of its commits, which duplicates changelog entries; squash gives one entry per pull request; rebase lists every commit.

## Decision

- **Windows: NSIS installer**, `Misign-<version>-windows-x64-setup.exe`, built by CPack from the installed tree. Qt's deployment script (`qt_generate_deploy_qml_app_script`, i.e. windeployqt) copies the Qt libraries, plugins and QML modules next to `misign.exe`.
- **Linux: AppImage**, `Misign-<version>-linux-x86_64.AppImage`, built by linuxdeploy with its Qt plugin (versions and SHA-256 pinned in `package.yml`) from the installed tree, which includes `packaging/linux/misign.desktop` and `packaging/icons/misign.svg`. It is built on the oldest supported GitHub runner (Ubuntu 22.04), because an AppImage only runs on systems whose glibc is at least as recent as the build system's.
- **Versions**: the project version lives in `CMakeLists.txt` (`VERSION x.y.z # x-release-please-version`), updated by release-please. Pre-releases add `MISIGN_VERSION_SUFFIX` (`-dev.N`), shown by the application and used in the installer names. Before 1.0, a breaking change bumps the minor version and a feature bumps the minor version.
- **Dev deployment** (`deploy-dev.yml`): on every push to `dev`, release-please runs as a dry run to get the next stable version `X.Y.Z` it would propose (or the next patch version when nothing user-facing changed), the installers are built, and a GitHub pre-release `vX.Y.Z-dev.N` is published, `N` counting the pre-releases of that version. Nothing is committed to `dev`.
- **Prod deployment** (`deploy-prod.yml`): on every push to `main`, release-please updates its release pull request (`CHANGELOG.md`, version, `.release-please-manifest.json`). Merging it creates the `vX.Y.Z` tag and the GitHub release; the workflow then attaches both installers and opens a pull request bringing `main` back into `dev`, so that `dev` has the release commit.
- **Release app**: release-please and the pull request back into `dev` use a token from a GitHub App (`RELEASE_APP_CLIENT_ID` variable, `RELEASE_APP_PRIVATE_KEY` secret). The default token can create neither, and pull requests it opens would not trigger the required CI checks. The app's commits are exempt from the DCO sign-off, like other bots.
- **Merge methods**: feature pull requests are **squashed** into `dev`, so the pull request title, checked by the "PR title" workflow, becomes the only changelog entry. `dev` is merged into `main`, and `main` back into `dev`, with **merge commits**: a squash would drop the release commit from the history of `dev`, and release-please would no longer find the last release.
- **Packaging checks**: `package.yml` also runs on pull requests that change the packaging, so a broken installer is caught before a release.

## Consequences

- Nothing is code-signed: Windows shows a SmartScreen warning, and users must trust the GitHub release. Signing can be added to the NSIS job later.
- Pre-release numbers are only unique because `deploy-dev.yml` never runs twice at the same time (concurrency group).
- Release-please ignores the `-dev.N` releases: in manifest mode it only accepts the release whose version is in `.release-please-manifest.json` (checked in the release-please 17.11 source).
- The GitHub App must be created and installed once (see `CONTRIBUTING.md`); until then `deploy-prod.yml` fails with an explicit error.
- PoDoFo is not packaged yet, because nothing links it: it joins both packages with the PoDoFo adapter (vcpkg ships PoDoFo 1.1.1 for Windows).
- The Windows window still has to be checked by hand on a native Windows host, from the first pre-release.
